# 안전한 리팩터링

## 수행 절차

1. 저장소 지침과 현재 변경 사항을 확인한다. 사용자 변경을 덮어쓰지 않는다.
2. 게임 규칙, 화면 동작, 공개 API의 함수 이름·인자·반환값·내보내기를 기록하고 개선 범위를 작게 정한다.
3. 변경 전 전체 기존 테스트를 실행하고 명령·통과 수·실패 수를 기록한다. 기존 실패 또는 실행 불가가 있으면 리팩터링을 시작하지 않고 차단 원인을 보고한다.
4. 변경 범위의 동작을 기존 테스트가 충분히 검증하지 못하면 의미 있는 회귀 테스트를 먼저 추가하고, 제품 코드 변경 전 모두 통과하는 기준 상태를 확보한다.
5. 기능과 공개 API를 유지하며 중복 제거, 내부 함수 분리, 내부 이름 개선 등 구조 변경을 직접 수행한다. 기능 추가와 버그 수정은 섞지 않는다.
6. 변경 후 동일한 전체 테스트를 실행하고 필요한 브라우저 시나리오를 확인한다. 새 실패가 생기면 자신의 리팩터링을 수정하거나 자신의 변경만 되돌린다.
7. 변경 파일, 구조 개선 내용, 변경 전후 테스트 증거와 남은 문제를 보고한다.

## 점검 체크리스트

- [ ] 변경 전 기준: 통과 — 전체 기존 테스트가 실행되어 모두 통과하고 결과를 기록했다. 실패 — 테스트 실패·미실행 또는 기록 누락이 있다.
- [ ] 검증 범위: 통과 — 변경할 동작과 경계값을 검증하는 테스트가 제품 코드 변경 전에 통과한다. 실패 — 구조 개선의 동작 보존을 확인할 테스트가 부족하다.
- [ ] 기능 유지: 통과 — 이동·회전·하강·고정·줄 제거·점수·종료·재시작 및 입력·표시가 변경 전과 같다. 실패 — 사용자 관찰 동작이나 규칙이 바뀐다.
- [ ] 공개 API 유지: 통과 — 외부에서 사용하는 함수·인자·반환값·내보내기 계약이 같다. 실패 — 호출자가 변경을 요구하거나 계약이 바뀐다.
- [ ] 구조 개선: 통과 — 변경이 중복 감소 또는 책임 분리 등 설명 가능한 개선을 제공한다. 실패 — 불필요한 추상화나 기능 변경이 섞인다.
- [ ] 사용자 변경 보존: 통과 — 기존 사용자 변경이 유지되고 자신의 범위만 수정했다. 실패 — 무관한 변경을 덮어쓰거나 되돌렸다.
- [ ] 변경 후 검증: 통과 — 변경 전과 동일한 전체 테스트가 모두 통과하고 필요한 UI 시나리오도 성공한다. 실패 — 회귀 실패 또는 미검증이 남는다.

## 보고 규칙

이 skill은 기능과 공개 API를 유지하는 범위에서만 코드를 직접 수정한다. 변경 전/후 각각의 테스트 명령, 실행 결과, 통과·실패 수를 제시하며 실행하지 않은 테스트를 통과했다고 쓰지 않는다. 검증 불가 시 완료로 보고하지 않는다.

남은 문제와 차단 원인은 `항목 | 심각도(높음·중간·낮음) | 개선안` 표로 보고한다. 높음은 기능·API 회귀 또는 상태 손상, 중간은 검증 부족·구조 개선 차단, 낮음은 후속 정리 사항이다. 문제가 없으면 “남은 문제 없음”과 검증 범위를 적는다.
